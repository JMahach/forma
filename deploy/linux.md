# Выпуск Формы 0.2 на Linux

Этот маршрут устанавливает согласованный коммит через существующие владельцы данных. Он не является подтверждением публикации. Рабочие данные остаются в `/var/lib/forma`, журнал в `/var/log/forma`, подготовленные расчёты в `/var/cache/forma`. Исходники и зависимости одного выпуска лежат в `/opt/forma/releases/<полный SHA>`, ссылка `/opt/forma/current` выбирает активный выпуск.

## 1. Подготовить выпуск без остановки сайта

Нужны Ubuntu 24.04, systemd ≥253, пользователь `forma`, Node 24 в `/opt/forma/node/bin`, Python 3.12 с venv и средствами сборки зависимостей. Почта устанавливается отдельно по [почтовой инструкции](postfix/linux.md). Её повторная установка не должна пересоздавать ключи, очередь или базу. Рабочую базу с компьютера разработчика на сервер не копируем.

Архитектор указывает полный SHA интегрированного коммита. На компьютере с этим коммитом создайте `git archive --format=tar <SHA>` и SHA-256 архива; передайте архив и контрольную сумму в закрытый временный каталог сервера. Не архивируйте рабочую папку: в ней могут быть `.env`, чужие изменения и местные данные. Сверьте контрольную сумму после передачи. SHA коммита здесь обозначает происхождение исходников; `FORMA_APP_VERSION` сам по себе не доказывает их целостность.

Распакуйте архив в **новый, ранее не существовавший** `/opt/forma/releases/<SHA>`, принадлежащий `forma:forma`. Не меняйте `current`. Из новой папки выполните от пользователя `forma`, с `/opt/forma/node/bin` в начале PATH:

```sh
npm ci
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
npm run build
```

Зависимости устанавливаются на Linux, а не копируются из macOS. Сборка создаёт собственный `dist`; общие подготовленные расчёты пока не трогаем. Убедитесь, что отсутствует `.env`, исходники включают `data/ephe`, а Python может импортировать `swisseph`. После сборки исходники и зависимости можно сделать принадлежащими root и доступными `forma` только для чтения; изменяемые данные находятся отдельно.

## 2. Проверить HTTPS и окружение до переключения

Домен `juxtaposition.ru` должен указывать на этот сервер. Для HTTPS необходим действующий сертификат именно этого домена в `/etc/letsencrypt/live/juxtaposition.ru/`. Проверка DNS, выпуск сертификата и принятие условий удостоверяющего центра — отдельные действия: наличие nginx-конфига их не выполняет.

При первом выпуске сертификата сохранить работающий HTTP-сайт, добавить только обработку `/.well-known/acme-challenge/` из `/var/lib/letsencrypt`, проверить `nginx -t` и доступность проверочного файла снаружи. После получения сертификата проверить имя, срок действия и цепочку доверия. Предусмотреть продление через установленный клиент сертификатов и перезагрузку nginx после успешного продления. До наличия сертификата не устанавливать конфиг с несуществующими TLS-файлами и не включать обязательный редирект.

Настройки из `forma.environment.example` размещаются в `/etc/forma/environment`, владелец `root:forma`, права `0640`, каталог `0750`. `FORMA_APP_VERSION` задаётся полным SHA **этого** выпуска непосредственно перед проверкой и запуском. `FORMA_LOCAL_MAILBOX=0`; разрешённый origin — `https://juxtaposition.ru`. При подключённом Telegram здесь же нужен согласованный числовой client ID. Почтовый файл `/etc/forma-postfix/environment` содержит только сокет и локальный SMTP-порт.

Проверить, что установленный `/etc/forma-postfix/control.json` ссылается на `/var/lib/forma/forma.sqlite`, UID пользователя `forma`, сокет своей очереди и `/var/log/forma/run/services.sock`. Нельзя подключать очередь к базе другого стенда. Если почтовые программы нужно обновить, используйте существующие `postfix/prepare.ts` и `postfix/install.py` из выбранного выпуска; не исправляйте базу вручную. Подключение выполняйте в остановленном окне ниже, после снимка базы; до конца проверки не запускайте отправку.

## 3. Одно окно остановки и один временный снимок

Записать старый путь `readlink -f /opt/forma/current`. Остановить `forma`, `forma-postfix` и отдельно запущенные задания подготовки; убедиться, что они действительно завершились. До завершения установки запросы посетителей могут получать временную ошибку. Это окно обслуживания, а не обещание обновления без перерыва.

Создать один закрытый каталог `/var/tmp/forma-release-backup` с правами `0700`. Если он уже существует — разобраться с прежним обновлением, не перезаписывать. Сохранить туда старый путь, действующие unit, environment и nginx-конфиг с закрытыми правами. Снимок базы делать SQLite Backup API, а не копированием одного файла при наличии WAL. Пример для уже существующей базы, от root, после остановки владельцев:

```python
import os, pathlib, shutil, sqlite3
os.umask(0o077)
backup = pathlib.Path('/var/tmp/forma-release-backup')
backup.mkdir(mode=0o700)  # если каталог существует, остановиться
source = sqlite3.connect('file:/var/lib/forma/forma.sqlite?mode=ro', uri=True)
target = sqlite3.connect(backup / 'forma.sqlite')
try:
    source.backup(target)
    if target.execute('PRAGMA integrity_check').fetchall() != [('ok',)]:
        raise RuntimeError('Backup integrity check failed')
finally:
    target.close()
    source.close()
shutil.copyfile('/var/lib/forma/keys/account-hmac.bin', backup / 'account-hmac.bin')
if (backup / 'account-hmac.bin').stat().st_size != 32:
    raise RuntimeError('Invalid existing account key')
```

Этот пример сам создаёт каталог; не создавайте его второй раз перед запуском. Затем добавьте перечисленные конфигурации и старый путь в тот же каталог. Ключ и база — одна пара; новый ключ поверх существующего не генерировать. Если базы ещё никогда не было, зафиксировать этот факт вместо создания фиктивной копии и проверить отсутствие почтовых заданий до первоначальной подготовки.

## 4. Подготовить данные и проверить связку

Команды выполняются из новой папки выпуска; `OLD_RELEASE` и `NEW_RELEASE` ниже — проверенные абсолютные пути, не произвольный ввод посетителя.

1. Из **новой** версии выполнить `python3 deploy/prepare-storage.py --release "$OLD_RELEASE"`, прочитать план, затем повторить с `--apply`. Так данные прежнего выпуска попадут в общую зону без дублирования многогигабайтной летописи. Если старого выпуска нет, этот шаг пропустить.
2. Аналогично выполнить план и `--apply` для `"$NEW_RELEASE"`. Конфликт двух заполненных каталогов или неверный владелец требуют разбора, а не удаления одной копии наугад. Совместимые подготовленные данные повторно не генерировать.
3. От пользователя `forma` выполнить `/opt/forma/node/bin/node --env-file=/etc/forma/environment deploy/prepare-accounts.ts`. Это существующий владелец схемы: он может обновить базу, поэтому снимок сделан **раньше**. Команда не подключает SMTP и не отправляет письма.
4. От root выполнить `/opt/forma/node/bin/node deploy/check-release.ts --release "$NEW_RELEASE" --revision "$REVISION"`.

`check-release.ts` только читает: проверяет окружение, приватные каталоги и ключ, совпадение базы/UID/сокетов приложения и почты, SMTP-порт, наличие Python и файлов готовой сборки. Он не открывает runtime, не мигрирует SQLite, не проверяет доставку письма, DNS, сертификат или работоспособность всех функций сайта. Проверка не заменяет следующие шаги.

## 5. Переключить и принять выпуск

Только после разрешения архитектора на интегрированный SHA установить новый `deploy/forma.service`, проверить `systemd-analyze verify`, заменить `current` атомарной ссылкой в `/opt/forma`, выполнить `systemctl daemon-reload` и запустить `forma-postfix`, затем `forma`. Перед запуском сохранить проверенные конфигурации из предыдущего шага. Установить `deploy/forma.nginx` вместо старого конфига этого сайта, проверить `nginx -t` и только затем перезагрузить nginx. Не добавлять второй экземпляр тех же `limit_*_zone`.

Проверить: службы активны без цикла перезапусков; Node слушает только `127.0.0.1:4173`; `/`, `/account`, `/library`, `/service-worker.js`, `/api/versions` доступны через HTTPS; `/api/account` без входа возвращает предусмотренный ответ гостя. Проверить заголовки и gzip/Brotli на реальных файлах из `dist/manifest.json`. Запрос публичной карты проверить на специально подготовленной карте, не перебирая чужие ID. Подготовленные летопись/возвраты должны читаться без новой длительной генерации. Приёмка под рабочими ограничениями systemd должна включать обычный расчёт и чтение готовых данных, а не только статус процесса.

Готовность летописи проверять отдельно после каждого запуска или перезапуска. Первый запрос к `/api/lifetime/meta` через существующий владелец проверяет контрольную сумму всего файла; открытый HTTP-порт этого ещё не подтверждает. В окне обслуживания дождаться ответа `200` от `http://127.0.0.1:4173/api/lifetime/meta`, записать длительность, затем проверить этот адрес через публичный HTTPS и один момент шкалы. Проверка может занять больше nginx `proxy_read_timeout`: первый публичный запрос тогда получает `504`, хотя проверка продолжается внутри процесса. Это воспроизводимый остаток холодного запуска, а не готовность всего сайта; успешный повторный запрос его не отменяет. Отдельная команда проверки файла не прогревает работающий процесс. Не увеличивать лимиты наугад, не пропускать проверку целостности и не пересоздавать готовые данные.

Настоящее письмо отправляется только по отдельному разрешению автора. Приёмка входа включает получение кода, вход, сохранение и открытие карты по ссылке; отдельный тест SMTP не доказывает этот полный путь. Телефон, Safari и обновление уже открытой вкладки проверяются автором на интегрированном выпуске.

## 6. Если запуск не удался

Остановить новую `forma` и почтовую очередь. **Возврат кода и восстановление данных — разные операции.** Вернуть старую ссылку и старый unit можно только после проверки совместимости старого кода с нынешней базой. Если совместимость неизвестна, сохранить данные и исправить выпуск; не пробовать старую программу на рабочей базе наугад.

Нельзя автоматически вернуть снимок базы после того, как новая версия приняла записи или отправила письма: исчезнут новые карты/входы, а уже доставленное письмо не отменится. Восстановление снимка требует отдельной проверки отсутствия новых записей и согласования последствий. Очередь Postfix не заменяется копией базы и не очищается произвольно.

После успешной приёмки удалить временный снимок, архив передачи и прежний каталог исходников, проверив, что `current` указывает на новый выпуск, а летопись и индекс возвратов действительно находятся в общей зоне. На сервере остаётся одна актуальная версия; постоянный склад старых выпусков или резервов этим маршрутом не создаётся.
