# Установка и эксплуатация Формы

Здесь описаны команды текущего проекта и порядок обслуживания. Устройство приложения и правила жизни данных — в [архитектуре](architecture.md). Наличие этой инструкции не подтверждает, что конкретный выпуск уже установлен или проверен на сервере.

## Локальная установка

Нужны Node **24.x**, npm и Python **3.12** с venv. Команды ниже выполняются из корня исходников, где лежит `package.json`. Если для Python-зависимости нет готового пакета, понадобятся системные инструменты сборки. Зависимости закреплены в `package-lock.json` и `requirements.txt`.

```sh
npm ci
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -c 'import swisseph; import zoneinfo'
```

Сервер вызывает Python именно из проектной `.venv`; эфемериды читает из `data/ephe`. Эти файлы должны входить в выпуск. На Windows путь интерпретатора — `.venv/Scripts/python.exe`; приведённые shell-команды рассчитаны на macOS/Linux.

В необязательной локальной `.env` задайте `FORMA_JOURNAL_WRITER=embedded`. Не заменяйте уже существующий файл целиком: в нём могут быть действующие пути стенда и почты. Для отдельной рабочей копии задайте собственные абсолютные `FORMA_STATE_DIR` и `FORMA_JOURNAL_DIR`, отдельный порт и отдельную браузерную сессию. Почтовую очередь чужого стенда не подключайте.

```sh
npm run prepare:lifetime
npm run prepare:returns
npm start
```

По умолчанию адрес — `http://localhost:3636`, слушатель — `0.0.0.0`. Для отдельного стенда, доступного только на этом компьютере: `HOST=127.0.0.1 PORT=4177 npm start`. Не занимайте уже работающий 3636. Для последующих запусков достаточно `npm start`: подготовленные данные повторно создавать не нужно.

Сборка и запуск выпуска:

```sh
npm run build
npm run start:release
```

Обычный запуск читает исходники, release-режиму нужен `dist/manifest.json`. Смена порта меняет origin и браузерное хранилище. Телефон в общей сети может открыть сетевой адрес компьютера, но его локальная библиотека отдельная; `localhost` телефона не указывает на компьютер.

## Окружение и места хранения

Параметры читаются из окружения процесса; сервер также загружает локальную `.env`. В боевом выпуске `.env` запрещена: systemd получает настройки из двух явно заданных файлов. Образец — [forma.environment.example](../deploy/forma.environment.example).

| Параметр | Смысл и значение |
| --- | --- |
| `HOST`, `PORT` | По умолчанию `0.0.0.0:3636`; служба сайта — `127.0.0.1:4173`. |
| `FORMA_STATE_DIR` | Абсолютный закрытый каталог аккаунтов; по умолчанию `~/.local/share/forma`, на сервере `/var/lib/forma`. |
| `FORMA_JOURNAL_DIR` | Отдельный абсолютный каталог журнала; локально по умолчанию `<state>/journal`, на сервере `/var/log/forma`. |
| `FORMA_ENVIRONMENT` | `stand` по умолчанию либо `production`. |
| `FORMA_JOURNAL_WRITER` | Обязательный выбор: `embedded` для местного запуска, `external` для отдельной службы журнала. Автоматической подмены режима нет. |
| `FORMA_JOURNAL_NGINX_SOCKET` | В боевом окружении `/run/forma-journal/nginx.sock`; источник событий nginx. |
| `FORMA_APP_VERSION` | В production обязателен полный SHA выпуска. Это версия приложения, не расчётов, и не самостоятельная проверка целостности исходников. |
| `FORMA_ACCOUNT_ORIGINS` | Разрешённые origins через запятую; локально по умолчанию localhost/loopback текущего порта, на сервере `https://juxtaposition.ru`. |
| `FORMA_TRUST_PROXY` | На сервере `loopback`: доверенный местный nginx. Другие значения не поддерживаются. |
| `FORMA_POSTFIX_SOCKET`, `FORMA_POSTFIX_PORT` | Задаются вместе: сокет управления очередью и её SMTP-порт; на сервере `/var/lib/forma-postfix/run/control.sock` и `2525`. Без пары почта не подключена. |
| `FORMA_TELEGRAM_CLIENT_ID` | Необязательный числовой ID зарегистрированного приложения Telegram. |
| `FORMA_LOCAL_MAILBOX` | `1` включает местный просмотрщик при допустимом локальном запуске; на сервере `0` или отсутствует. Само значение не перенастраивает Postfix. |
| `TRANSIT_CACHE_DIR` | Путь прежнего дискового кэша транзитных дней для его очистки; локально `.cache/transit`, systemd задаёт `/var/cache/forma/transit`. Новые транзитные дни хранятся в RAM, не в этом каталоге. |

| Данные | Где находятся и как обращаться |
| --- | --- |
| Аккаунты, карты, подготовленные пакеты библиотеки, пометки операций | `<state>/forma.sqlite`; это постоянная серверная база. Не заменять базой с другого стенда. |
| Ключ подписей аккаунта | `<state>/keys/account-hmac.bin`, 32 байта. Сохранять вместе с базой, не создавать новый поверх прежнего. |
| Журнал | `<journal>/archive`, вспомогательные данные и `<journal>/run/services.sock`; на сервере отдельный владелец записи `forma-journal`. |
| Летопись | `.cache/lifetime/lifetime-1801-2400.f64le` и соседний `.metadata.json`. На сервере каталог связан с `/var/cache/forma/lifetime`. |
| Индекс возвратов | `.cache/returns/return-index.bin`; на сервере каталог связан с `/var/cache/forma/returns`. |
| Код и сборка | `/opt/forma/releases/<SHA>`; `/opt/forma/current` — ссылка на действующий выпуск. |
| Почтовая очередь | Временные тела писем — `/var/spool/forma-postfix`, служебные программы/данные — `/var/lib/forma-postfix`, настройки — `/etc/forma-postfix`. |
| Подпись почты | `/etc/forma-dkim`; приватный DKIM-ключ сохраняется при обновлении. |
| Копии браузера | IndexedDB и кэш приложения соответствующего origin на устройстве; это не резервная копия всей серверной базы. |

## Подготовленные файлы

Летопись и индекс возвратов общие для всех людей. Они не входят в Git и не создаются запуском сайта. Летопись содержит готовые числовые точки; индекс помогает находить участки для уточнения времени возврата. Проверка индекса без пересчёта:

```sh
npm run prepare:returns -- --check
```

Сервер проверяет формат и контрольную сумму готовой Летописи до открытия HTTP, затем читает отдельные точки. Поэтому активный процесс systemd ещё не означает готовый сайт. Отсутствующий/ещё не готовый набор оставляет ограниченный режим: `/api/lifetime/meta` отвечает `503 lifetime_preparing`; готовые файлы обнаружатся при следующем обращении. Повреждённый готовый набор блокирует запуск. Не меняйте содержимое открытого файла на месте.

Без подходящего индекса поиск дат медленнее, а открытие возврата планеты/узлов, которому нужна проверка полного оборота, недоступно. Перед приёмкой выпуска нужны оба набора.

### Однократный переход прежних файлов

Он **не запускается автоматически** ни через HTTP, ни при старте, ни обычной подготовкой. Остановите читателей и подготовительные задания. Укажите только существующие файлы; команда допускает один из двух аргументов, но не допускает отсутствие путей:

```sh
node scripts/migrate-prepared-calculations.ts \
  --lifetime .cache/lifetime/lifetime-1801-2400.f64le \
  --returns .cache/returns/return-index.bin
```

Числа не пересчитываются. У Летописи атомарно заменяются метаданные после проверки числового файла. У индекса заменяется заголовок с копированием неизменённого числового блока; нужно свободное место для временной копии индекса. Владелец и права сохраняются, повтор команды допустим. Обратного CLI-перехода нет: совместимость старого читателя с новым форматом нужно проверить до выпуска.

## Местная почта

На macOS приёмник устанавливает `python3 deploy/local_mailbox.py install`: закреплённый Mailpit с проверкой скачанного файла, пользовательская служба, HTTP `127.0.0.1:8025`, SMTP с STARTTLS `127.0.0.1:1025`. Служебные файлы находятся в `~/.local/share/forma-mailbox`; база писем временная, штатный перезапуск очищает её. Это не архив кодов входа.

Для просмотра через `/__mail/` нужны `FORMA_LOCAL_MAILBOX=1`, `stand`, обычный запуск без `--release` и обращение с этого компьютера через localhost/loopback. Просмотрщик и маршрут доставки — разные настройки. В местном Postfix подготовитель запускают с `--local-mailbox-port 1025`; тогда все пользовательские письма идут в местный ящик, и при его остановке интернет-доставка не включается. Сам установщик Mailpit не изменяет Postfix, сайт или DNS.

Для подготовки местной очереди используйте [prepare.ts](../deploy/postfix/prepare.ts) от владельца локальной базы, с новым абсолютным `--output`, явным `--database`, `--journal-socket` и `--local-mailbox-port 1025`. Затем просмотрите комплект и план `python3 <комплект>/install.py --bundle <комплект>`; применение требует `--apply` и прав администратора. Установщик использует фиксированный системный экземпляр очереди: его нельзя повторно подключить к другому стенду, сохранив прежнему стенду ту же очередь.

## Боевые службы и почта

Маршрут сайта: HTTPS nginx → Node на `127.0.0.1:4173` → проектный Python и постоянное хранилище. [forma.service](../deploy/forma.service) работает от `forma`, [forma-journal.service](../deploy/forma-journal.service) владеет единым журналом. Обе службы перезапускаются при отказе с задержкой 5 секунд. В шаблонах заданы `MemoryMax=400M` для сайта и `256M` для журнала, `CPUQuota=50%` у каждой службы; это параметры шаблона, а не измеренный предел нагрузки. Журнал не переключается на встроенный режим при отказе отдельной службы.

Журнал ограничен 500 000 000 байт и 30 днями; это диагностическое хранение, не копия пользовательской библиотеки. Службы передают ограниченные сведения о сбое через закрытый сокет. Если writer недоступен, разовая служебная отправка может не сохраниться. Не переименовывайте и не удаляйте сокеты при живом владельце; сначала дождитесь его остановки.

Почта — отдельный экземпляр Postfix и подписант OpenDKIM. Приём приложения слушает только `127.0.0.1:2525`, подписант — `127.0.0.1:8891`; исходящая доставка идёт к чужим SMTP-серверам. Входящие ящики этот комплект не создаёт. Очередь ограничена 500 письмами / 10 МиБ и ожиданием до 5 минут; постоянного архива тел писем нет. Контроллер очереди имеет `Restart=always`, 5 секунд до перезапуска; необработанный сбой очистки завершает контроллер для восстановления службой.

### Первое подключение почты и обновление её программ

Нужны системные Postfix/OpenDKIM, отдельный настроенный `forma-dkim.service`, закрытый ключ `/etc/forma-dkim/forma.private`, домен `juxtaposition.ru` и selector `forma`. Подписант работает от `opendkim`, с `Mode s`, `Socket inet:8891@[127.0.0.1]`, без сырых журналов писем. Системные экземпляры Postfix/OpenDKIM не должны запускать дополнительный входящий SMTP. На пустом сервере установку пакетов и подписанта проводят отдельно до подключения приложения: готового установщика всей этой части в репозитории нет.

Для новой установки один раз создают DKIM-ключ и публикуют **публичное** значение в `forma._domainkey.juxtaposition.ru`; при обновлении ключ сохраняют. Проверяют A/PTR имени `mail.juxtaposition.ru`, единственную SPF и DMARC. Существующие MX и сторонние TXT не заменяют. Настройки прежнего IP из старых записей не подтверждают нынешний DNS. Собственный HTTPS-сертификат сайта не нужен для исходящего STARTTLS. Почтовая политика требует шифрование, но не задаёт проверку имени чужого сертификата в режиме `verify`.

На подготовленном сервере из нового выпуска, после создания/подготовки базы и её снимка, команды root:

```sh
runuser -u forma -- /opt/forma/node/bin/node deploy/postfix/prepare.ts \
  --output /var/tmp/forma-postfix-prepared \
  --database /var/lib/forma/forma.sqlite --port 2525 \
  --dkim-port 8891 --journal-socket /var/log/forma/run/services.sock
/usr/sbin/postconf -c /var/tmp/forma-postfix-prepared -e 'inet_protocols=ipv4'
chown -R root:root /var/tmp/forma-postfix-prepared
chmod -R go-rwx /var/tmp/forma-postfix-prepared
python3 /var/tmp/forma-postfix-prepared/install.py --bundle /var/tmp/forma-postfix-prepared
# После просмотра плана установки:
python3 /var/tmp/forma-postfix-prepared/install.py --bundle /var/tmp/forma-postfix-prepared --apply
```

Каталог комплекта должен быть новым. Подготовитель фиксирует UID вызывающего пользователя, поэтому его запускают от `forma`, а не root. IPv4 сохраняет существующую схему доставки; подключение IPv6 требует согласованного DNS. В production не указывают `--local-mailbox-port`. Установщик сохраняет очередь и базу, но **сам запускает почтовую службу**: при обновлении сайта выполняйте его после резервного снимка, держите веб-приложение остановленным, затем снова остановите `forma-postfix` до общего старта. Если отправка в этот момент недопустима, сначала дождитесь пустой очереди; у установщика нет флага «установить без запуска».

Окружение приложения установщик не меняет. `/etc/forma-postfix/environment` должен содержать только:

```dotenv
FORMA_POSTFIX_SOCKET=/var/lib/forma-postfix/run/control.sock
FORMA_POSTFIX_PORT=2525
```

`control.json` обязан указывать ту же базу, UID `forma` и `/var/log/forma/run/services.sock`. Приватный ключ не печатайте. Настоящее проверочное письмо требует разрешения автора; статус службы или синтетический SMTP не доказывают доставку в реальный ящик.

Для отдельного комплекта только почтовых служебных программ выполните `node deploy/postfix/package-linux.ts --output /абсолютный/новый/каталог`. Он собирает существующих владельцев в `deploy/prepare-accounts.mjs` и `deploy/postfix/prepare.mjs`, добавляет программы установщика, документацию и `SHA256SUMS`; службы не запускает. После передачи проверьте `sha256sum -c SHA256SUMS`. В приведённых выше командах такого комплекта используйте `.mjs` вместо исходных `.ts`. Этот комплект не является выпуском сайта; ссылки на исходный код в документации относятся к полному репозиторию.

## Выпуск и обновление на Linux

Порядок рассчитан на Ubuntu 24.04, systemd ≥253, пользователя `forma`, Node 24 в `/opt/forma/node/bin`, Python 3.12 и подготовленную почту. Нужны nginx и действующий сертификат `juxtaposition.ru` в `/etc/letsencrypt/live/juxtaposition.ru/`. DNS, выдача/продление сертификата и перезагрузка nginx после продления настраиваются отдельно; конфиг проекта их не выполняет. Серверные блоки выполняйте в отдельной root-сессии с `set -eu`: при ошибке не продолжайте следующий шаг. Команды с `runuser` сами переходят к пользователю приложения.

### 1. Собрать новый выпуск до остановки

Выберите полный SHA интегрированного коммита. На машине с этим коммитом задайте `REVISION`, затем создайте архив исходников и его контрольную сумму; не архивируйте рабочую папку с `.env` и местными данными:

```sh
: "${REVISION:?Задайте полный SHA выпуска}"
git archive --format=tar --output="/tmp/forma-$REVISION.tar" "$REVISION"
shasum -a 256 "/tmp/forma-$REVISION.tar"
```

Передайте архив в закрытый временный каталог сервера и сравните `sha256sum` с полученной суммой. Распакуйте в новый, прежде не существовавший `/opt/forma/releases/<SHA>`, владелец `forma:forma`; не меняйте `current`. В новом каталоге от `forma`, с `/opt/forma/node/bin` в начале PATH:

```sh
npm ci
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -c 'import swisseph'
npm run build
test ! -e .env
```

Зависимости собираются на Linux, не переносятся с Mac. Проверьте наличие `data/ephe`. В дальнейшей root-сессии задайте `REVISION`, `NEW_RELEASE=/opt/forma/releases/$REVISION` и, при обновлении, `OLD_RELEASE` по `readlink -f /opt/forma/current`; работайте из `NEW_RELEASE`. Это проверенные абсолютные пути. Не перезаписывайте существующий каталог выпуска.

### 2. Подготовить окружение

`/etc/forma/environment`: каталог `root:forma` с правами `0750`, файл `root:forma` с правами `0640`. Заполните по образцу, задайте SHA в `FORMA_APP_VERSION`, `production`, `external`, публичный origin и `FORMA_LOCAL_MAILBOX=0`. Почтовое окружение храните отдельно, с закрытой записью для root. Сохраните прежние настройки перед изменением. У нового выпуска не должно быть локальной `.env`.

Конфиг [forma.nginx](../deploy/forma.nginx) включается в контексте `http`. Он требует существующих TLS-файлов; до получения сертификата оставляют рабочий HTTP и обработку ACME, а не включают конфиг с отсутствующим сертификатом. Лимиты расчётов, диагностики и возвратов уже заданы шаблоном.

### 3. Остановить владельцев и сделать снимок

Это окно обслуживания: во время остановки/проверки файла посетители могут получить `502`. Запишите старый путь выпуска; остановите отдельно запущенные задания подготовки и дождитесь их завершения. Остановите сайт и почтовую очередь, затем журнал (при первой установке отсутствующие службы пропускают):

```sh
systemctl stop forma.service forma-postfix.service
systemctl stop forma-journal.service
```

Убедитесь, что процессы завершились. Для существующей базы используйте SQLite Backup API, а не копию одного файла рядом с WAL. Следующий блок root сам создаёт **новый** закрытый каталог; если он уже есть, сначала разберите прежнее обновление:

```sh
python3 - <<'PY'
import os, pathlib, shutil, sqlite3
os.umask(0o077)
backup = pathlib.Path('/var/tmp/forma-release-backup')
backup.mkdir(mode=0o700)
source = sqlite3.connect('file:/var/lib/forma/forma.sqlite?mode=ro', uri=True)
target = sqlite3.connect(backup / 'forma.sqlite')
try:
    source.backup(target)
    if target.execute('PRAGMA integrity_check').fetchall() != [('ok',)]:
        raise RuntimeError('Backup integrity check failed')
finally:
    target.close()
    source.close()
shutil.copyfile('/var/lib/forma/keys/account-hmac.bin', backup / 'account-hmac.bin')
if (backup / 'account-hmac.bin').stat().st_size != 32:
    raise RuntimeError('Invalid existing account key')
PY
```

Добавьте в тот же закрытый каталог старый путь выпуска, действующие units/drop-ins, окружение и nginx-конфигурацию. База и HMAC-ключ — пара. При первой установке зафиксируйте отсутствие прежней базы; не создавайте фиктивный резерв и не копируйте базу разработчика. Это временный снимок окна выпуска, не автоматически работающая система резервирования. Если для отката нужны прежние форматы, сохраните до перехода метаданные Летописи и индекс возвратов: обычный снимок SQLite их не включает. Неизменяемый числовой файл Летописи этот переход не переписывает.

### 4. Подготовить хранилище и выполнить переход

Команды из **нового** выпуска. Сначала план, затем применение от root:

```sh
# Только при наличии прежнего выпуска:
python3 deploy/prepare-storage.py --release "$OLD_RELEASE"
python3 deploy/prepare-storage.py --release "$OLD_RELEASE" --apply
# Для нового выпуска:
python3 deploy/prepare-storage.py --release "$NEW_RELEASE"
python3 deploy/prepare-storage.py --release "$NEW_RELEASE" --apply
runuser -u forma -- /opt/forma/node/bin/node --env-file=/etc/forma/environment deploy/prepare-accounts.ts
```

Помощник переносит существующие каталоги Летописи/индекса в общую зону и ставит ссылки, не копируя многогигабайтный файл. Конфликт двух заполненных каталогов, другой диск или неверные права требуют разбора. Подготовленные файлы должны принадлежать `forma` и читаться им; помощник не исправляет их рекурсивно. `prepare-accounts.ts` открывает/обновляет схему базы без подключения SMTP: поэтому резерв сделан раньше.

**До запуска новых читателей** выполните миграцию прежних подготовленных файлов из раздела выше, теперь от `forma`:

```sh
runuser -u forma -- /opt/forma/node/bin/node scripts/migrate-prepared-calculations.ts \
  --lifetime .cache/lifetime/lifetime-1801-2400.f64le \
  --returns .cache/returns/return-index.bin
```

Если есть только один набор, оставьте только соответствующий аргумент. Если обоих ещё нет, переход пропустите; генерация описана ниже. Не подменяйте миграцию пересчётом готовых чисел. Для индекса обеспечьте место под временную копию. Старые процессы в этот момент должны быть остановлены.

При необходимости обновите программы почты описанным выше способом, сохраняя базу, очередь и DKIM-ключ. После подготовки выполните от root:

```sh
/opt/forma/node/bin/node deploy/check-release.ts --release "$NEW_RELEASE" --revision "$REVISION"
```

Это только чтение: окружение, права, ключ, совпадение базы/UID/сокетов, SMTP-порт, версия Node, наличие Python и сборки. Проверка не запускает сайт, не проверяет Python-импорты, числовые файлы, DNS, сертификат или доставку письма и не изменяет SQLite.

### 5. Переключить и проверить

Установите из выпуска `deploy/forma.service` и `deploy/forma-journal.service` в `/etc/systemd/system/`, `deploy/nginx-journal.conf` — в `/etc/systemd/system/nginx.service.d/forma-journal.conf`, `deploy/postfix-journal.conf` — в `/etc/systemd/system/forma-postfix.service.d/forma-journal.conf`. Не теряйте почтовый drop-in при обновлении основного unit. Проверьте units через `systemd-analyze verify`.

Пример атомарного переключения на Linux из root-сессии; временное имя должно быть свободно:

```sh
set -eu
test ! -e /opt/forma/current.next
test ! -L /opt/forma/current.next
ln -s "$NEW_RELEASE" /opt/forma/current.next
mv -Tf /opt/forma/current.next /opt/forma/current
systemctl daemon-reload
systemctl enable forma-journal.service forma.service
systemctl start forma-journal.service
systemctl start forma-postfix.service forma.service
```

Журнал имеет `Type=notify`: дождитесь успешного старта. Установите nginx-конфиг в принятую на сервере точку подключения без повторных limit-зон; выполните `nginx -t` и только после успеха `systemctl reload nginx`. Если сертификат ещё не готов, этот шаг не выполняют.

Если подготовленных файлов раньше не было, создайте их от `forma` после подключения общей зоны и запуска журнала, из нового выпуска:

```sh
runuser -u forma -- /opt/forma/node/bin/node --env-file=/etc/forma/environment scripts/python.ts \
  -m server.python.lifetime_file --file .cache/lifetime/lifetime-1801-2400.f64le
runuser -u forma -- /opt/forma/node/bin/node --env-file=/etc/forma/environment scripts/python.ts \
  -m server.python.return_index --file .cache/returns/return-index.bin
```

Совместимые готовые данные заново не генерируйте. Прежде чем объявлять сайт готовым, дождитесь HTTP и `200` от `http://127.0.0.1:4173/api/lifetime/meta`. `systemctl is-active` этого не доказывает: запуск проверяет большую Летопись до открытия порта. Фиксированного обещания времени запуска нет.

Проверьте через HTTPS `/`, `/account`, `/library`, `/service-worker.js`, `/api/cities?q=Moscow`, гостевой ответ `/api/account`; затем обычный расчёт, чтение Летописи, возврат и специально подготовленную публичную карту. Проверьте заголовки/сжатие реальных файлов `dist`, отсутствие цикла рестартов, loopback-слушатель Node. Переключение уже открытых вкладок и сохранность пользовательской работы проверяют на полном интегрированном выпуске. Не смешивайте старый клиент с половиной нового серверного контракта.

### 6. Откат и завершение

Если новый выпуск не принят, остановите сайт и почту, затем журнал. Возврат кода допускается только после проверки, что старый код читает нынешние SQLite и подготовленные файлы. Верните вместе старую ссылку, units/drop-ins, окружение и nginx-конфиг; встроенный и внешний владельцы журнала не должны работать одновременно. Повторите проверку конфигураций и готовности.

Восстановление базы — отдельное решение. После новых записей или отправки писем автоматический возврат снимка потеряет принятые изменения; отправленное письмо назад не вернуть. Снимок должен сохранять полный реестр `chart_identifiers`: выданные адреса не становятся свободными после удаления карты. При разрешённом восстановлении останавливают всех владельцев, сохраняют нынешнее состояние отдельно, восстанавливают согласованную базу с её ключом и правами `forma`, учитывают оставшиеся WAL/SHM и согласованность почтовой очереди. Не накладывайте старый `.sqlite` поверх живой базы.

Если совместимость неизвестна, сохраните данные и исправьте выпуск; не пробуйте старую программу на рабочей базе наугад. После успешной приёмки удаляют согласованные временные архив передачи, снимок и прежний каталог исходников. Перед этим проверяют `current` и фактическое размещение Летописи/индекса в общей зоне. Постоянное автоматическое резервирование этой процедурой не создаётся.

## Быстрая диагностика

| Симптом | Что проверить |
| --- | --- |
| `EADDRINUSE` | Кто уже владеет выбранным портом; не завершать все процессы Node. |
| Нет `.venv/bin/python` / `swisseph` | Установку Python-зависимостей именно в этом выпуске. |
| Нет `dist` / manifest | Выполнена ли сборка для release-режима. |
| Процесс активен, HTTP ещё закрыт | Проверку Летописи; статус процесса не равен готовности. |
| `503 lifetime_preparing` | Наличие обоих файлов Летописи и состояние отдельно запущенной подготовки. |
| Повреждённый готовый файл | Остановить читателей, проверить файл/формат; не обходить контроль целостности. |
| Вход не отправляет письмо | Пару SMTP/сокет, UID и путь базы в `control.json`, службу очереди, подписант; локально — маршрут в Mailpit. |
| Нет служебных событий | Явный режим writer, службу журнала, права и путь сокета; не включать второй writer. |

Пути и флаги CLI определяются [deploy](../deploy/) и [миграцией подготовленных данных](../scripts/migrate-prepared-calculations.ts). Инструкция не заменяет проверку фактических DNS, места на диске, прав, служб и совместимости выбранного старого выпуска перед реальной публикацией.
